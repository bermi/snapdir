Release notes

snapdir 1.9.0

Three operator-prioritized fixes, each rediscovered and verified by an independent adversarial QA pass: a default-on catalog, a panic-free / crash-free directory walk under concurrent file change, and a documented shell-completion command.

1 · Catalog

The catalog is on by defaultfixbehavior

You created snapshots without --catalog, then ran revisions --catalog none and got nothing back. The write path logged to no catalog at all, while --catalog none opened a literal, always-empty none-catalog.redb — two halves that never met.

Before (1.8.0)

  • push/stage without --catalog → recorded to no catalog.
  • revisions --catalog none → silently empty (queried an empty DB named none).
  • Snapshots taken without a flag were un-queryable.

After (1.9.0)

  • --catalog unset → a default catalog; push/stage auto-record, queries read it.
  • No-flag snapshots are now queryable out of the box.
  • --catalog none = explicit disable sentinel → a clear "catalog disabled" message, not a fake-empty result.
# 1.8.0 — snapshots made, but nothing comes back $ snapdir push ./CleanedUpBooks --store … # (no --catalog) $ snapdir revisions --catalog none --location ./CleanedUpBooks (nothing) # 1.9.0 — the no-flag snapshot is recorded and listed $ snapdir revisions --location ./CleanedUpBooks ce0dca… 2026-06-17 ./CleanedUpBooks

2 · Robustness — files changing mid-snapshot

A tree in flux fails loudly & safely — never silentlyfix

Hashing a directory whose files were being written, truncated, or deleted could end three bad ways: a hard SIGBUS process kill with no output at all, a Rust panic with a backtrace, or a quietly-wrong recorded size. 1.9.0 turns every in-flux condition into a clear, typed error that names the offending file and exits non-zero.

Before (1.8.0)

  • Large file truncated mid-hash (mmap) → SIGBUS kills the process, prints nothing.
  • Directory vanishes mid-walk → panic + backtrace (two expect() sites).
  • File grows mid-hash → silently records the wrong size.
  • Deleted file → generic IO error (mislabeled a transient race).

After (1.9.0)

  • Scoped SIGBUS handler → truncation becomes a clean file changed during walk error (links on macOS and glibc/musl Linux).
  • The two panics → typed tree structure changed during walk returns.
  • Grow/shrink caught by a stat + bytes guard → file changed during walk, never a wrong size.
  • Deleted file → file vanished during walk, naming the path, exit ≠ 0.
Consistency model: snapdir assumes a quiescent tree during a snapshot. Outcome is now always either a valid 64-hex snapshot id (exit 0) or a typed error naming the file (exit ≠ 0) — never a silent kill, never a panic, never a wrong size. On a static tree, ids and manifests are byte-identical to before (the frozen-format keystone holds).

3 · Shell completions

snapdir autocomplete <shell>new

A completion command existed but was hidden and undocumented. 1.9.0 promotes it to a first-class, documented command with profile-wiring help — the way gh and rustup do it.

Before (1.8.0)

  • completions existed but was hidden from --help.
  • No documentation, no wiring guidance.

After (1.9.0)

  • snapdir autocomplete <shell> — visible & documented, for bash · zsh · fish · powershell · elvish.
  • Long-help shows exactly how to wire it into your profile.
  • An unknown shell fails fast (exit 2) listing the valid shells; completions stays as a back-compat alias.
# add to ~/.zshrc (or ~/.bashrc with 'bash') $ eval "$(snapdir autocomplete zsh)"

How it was built

Each fix shipped as an adversarial triple — an independent agent wrote the black-box tests from the spec alone, a separate lane wrote the source, and a third reviewed for weakening — coordinated by a gate ledger (3 clusters + a 5-gate release chain). A Linux-only linker bug in the SIGBUS handler (sigsetjmp is a macro over __sigsetjmp on glibc) was caught by CI, reopened, fixed, and re-verified before release. The frozen manifest/merkle format was never touched.
